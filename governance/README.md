# GitHub 项目组合治理

本目录是 `weepwood` 名下仓库的项目组合治理入口，用于回答三个问题：

1. 哪些仓库仍在维护；
2. 不同仓库需要多强的工程治理；
3. 哪些设置、模板和自动化应在仓库之间复用。

项目目录网站继续负责展示公开项目与在线状态；本目录负责项目分级、生命周期和治理策略，两者不重复维护生成数据。

## 治理原则

- 先减少活跃仓库数量，再增加流程。
- 正式产品与实验项目采用不同治理强度。
- `projects.yml` 是项目等级与生命周期状态的机器可读事实来源。
- 仓库归档、改名和历史重写必须先人工确认，不由自动化直接执行。
- AI 可以调查、生成候选清单和提交治理 PR，但不能仅凭仓库名称删除或归档项目。
- 关键项目要求风险、边界、验证、回滚和独立审查；小型实验只保留最低必要约束。

## 项目等级

### S：关键正式项目

适用于生产系统、敏感数据系统和长期正式交付项目。

最低要求：

- 只能通过 PR 修改正式主分支；
- required checks、对话解决、禁止 force push 和主分支删除；
- `AGENTS.md`、`ARCHITECTURE.md`、风险分级和回滚说明；
- 高风险变更必须有关联 Issue、失败路径测试和独立审查；
- 发布版本、兼容范围和数据迁移必须可追踪。

### A：持续开发的产品

适用于仍在持续开发、可能拥有真实用户或远端数据的产品。

最低要求：

- `README.md` 和精简版 `AGENTS.md`；
- lint、typecheck、test、build 等与技术栈匹配的 CI；
- PR 模板、Dependabot 和主分支保护；
- Issue 与 PR 关联，明确数据与安全边界；
- 发布、预览或部署状态可判断。

### B：可维护的小工具与作品

适用于功能边界清晰、风险较低的小型工具和展示项目。

最低要求：

- README 说明用途、运行方式和项目状态；
- 基础 CI；
- 默认 squash merge；
- 部署项目应有构建与在线状态检查。

### Lab：实验与学习项目

适用于 UI、算法、语言和技术验证项目。

最低要求：

- 明确标注 `experimental`；
- README 说明实验目标和当前结论；
- 不默认启用高噪声依赖更新；
- 同类小实验优先合并到专题 Lab 仓库。

### Archive：停止维护

适用于被替代、长期无维护计划、重复或仅保留历史参考的仓库。

归档前应：

- 说明停止维护状态；
- 指向替代项目（如有）；
- 确认没有仍在使用的部署、自动化或外部依赖；
- 保留仓库，不直接删除。

### Mirror：镜像或上游副本

镜像仓库不应被误认为自主维护产品，应明确上游来源、同步方式和本地改动边界。

## 生命周期状态

允许值：

- `active`：正式维护中；
- `developing`：快速开发中；
- `maintenance`：只接受修复和必要升级；
- `experimental`：实验阶段；
- `paused`：暂停但尚未放弃；
- `archive-candidate`：待人工复核归档；
- `archived`：已归档；
- `mirror`：镜像或同步副本。

## 变更流程

1. 修改 `projects.yml`；
2. 在 PR 中说明分级依据、状态变化和影响；
3. 涉及归档、改名或迁移时附上检查证据；
4. 合并后再执行 GitHub 仓库设置变更；
5. 记录未能通过 API 自动完成的设置。

## 当前实施边界

本阶段先建立项目分级、模板、可复用工作流和设置清单。GitHub Ruleset、仓库归档、默认合并方式等设置需要在仓库 Settings 中执行；在确认前不批量改变现有仓库。
